# 系统架构说明

## 分层

```text
前端 / API 网关
       ↓
src/api（居民、工作人员、管理员接口域）
       ↓
src/service（业务编排与事务边界）
       ↓
src/agent（意图、调度、流转、积分、巡检）
       ↓
src/dao → src/models → PostgreSQL / SQLite
       ↓
src/extensions（Redis、MinIO）
```

API 层仅负责鉴权、参数和响应；Service 层承载用例与事务；DAO 隔离查询；Agent 由 `AgentEngine` 按配置流水线串行执行，结果写入共享 `AgentHub`。默认开发环境使用 SQLite 与本地协调锁，生产环境通过环境变量切换 PostgreSQL、Redis、RabbitMQ 和 MinIO。

## 核心链路

1. 居民先上传图片、音频或视频；文件写入 R2、MinIO 或开发环境本地目录，元数据与所有权单独保存。
2. 多模态融合服务标准化文字、图像标签和语音转写。
3. 意图 Agent 识别分类、优先级、置信度与标签。
4. 工单持久化并记录流转事件。
5. 调度 Agent 根据优先级、区域和风险制定调度计划，依次调用候选人筛选、距离计算和可解释评分工具；普通工单采用技能 45%、负载 25%、距离 20%、评分 10% 的均衡权重，紧急工单提高距离权重。
6. 调度服务在工单锁内完成派单、负载更新和审计事件写入。
7. 流转 Agent 校验状态机；完成后积分 Agent 自动结算。
8. Celery 异步富化（语音/图像/大模型）与定时巡检、积压捞回。

## Agent 化调度边界

调度 Agent 不直接修改数据库，也不让大模型绕过业务约束。它围绕“找到安全且合适的处理人”执行 Observe → Plan → Act → Evaluate：

1. 观察工单优先级、类别、区域与人员池。
2. 动态生成策略序列：本区专业人员、跨区专业人员、允许时的综合人员兜底。
3. 调用确定性的筛选和评分工具，并在无候选人时切换下一策略。
4. 输出处理人、候选方案、策略、权重、置信度及完整决策轨迹；安全隐患无合格人员时转人工调度。

固定公式只是 Agent 的一个可审计工具。Redis 锁、人员容量、状态机和数据库事务仍由确定性服务保证，避免智能决策破坏业务一致性。

## 降级策略

- Redis 不可用：退化为单实例内存锁和 L1 缓存。
- 大模型不可用：主模型熔断后切备用模型，再不可用则规则摘要兜底；语音/视觉同样熔断降级。
- RabbitMQ 不可用：同步接口不受影响（Celery 异步任务会暂停）。
- MinIO 不可用：`MEDIA_STORAGE_MODE=auto` 自动退化为受控本地目录；生产环境可设置为 MinIO 强制模式。

## 在线运行架构

Sites 版本使用同一套业务界面，结构化数据保存到 D1，附件字节保存到 R2。`app/api/platform` 在服务端完成身份识别、权限检查、文件校验、状态机、派单和评价，浏览器不保存权威业务数据。Python/FastAPI 版本用于独立部署与企业内网集成，两者的领域模型和流转规则保持一致。

## 权限

- resident：注册、登录、创建与查看本人工作单、评价和积分查询。
- worker：查看本人任务、更新处理状态、查看绩效。
- admin：全局查询、智能派单、改派、督办、用户与系统配置、统计。
